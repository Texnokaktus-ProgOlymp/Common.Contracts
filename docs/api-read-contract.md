# API contest and registration read contract

`proto/Api/ApiReadService.proto` adds two unary reads in the separate
`progolymp.api` protobuf package. It leaves every existing service and message
unchanged. The C# namespace is
`Texnokaktus.ProgOlymp.Common.Contracts.Grpc.Api`.

- `ListContests` returns the API-owned numeric contest ID, stable contest name,
  display title and optional external contest ID for each stage.
- `GetRegistrationSnapshot` selects one numeric API contest ID and returns that
  metadata with its complete registration roster. Each registration carries the
  API application ID, user ID, grade, region, registration name and optional
  external participant ID for each stage.

`Registration` belongs to `RegistrationSnapshot` and is nested in that message.
`ContestMetadata` is shared by the catalog and snapshot. Field numbers and types
are the wire contract. New fields must be additive; removed fields must have
both their numbers and names reserved.

## Identity and presence

The API contest, application and user IDs are independent Int32 keys. An external
contest ID is an Int64 competition binding. An external participant ID is a
separate Int64 key within that stage's competition; it is not the API application
ID, the API user ID or the competition ID. Preliminary and final participant IDs
may differ.

Optional stage bindings, participant IDs and patronymic have protobuf presence.
An absent value is not replaced with zero or an empty string. Protobuf itself can
encode a present default value; the API validates actual identities instead of
using default values as invented registrations. A missing stage participation
says nothing about the participant's start, attempts or score.

The server returns the complete roster or a gRPC error, never a partially loaded
successful snapshot. A successful empty roster retains the selected contest
metadata. An empty catalog is valid. A nonpositive requested contest ID is
`InvalidArgument`; a missing contest is `NotFound`. Server cancellation must
reach the database query. These are server implementation obligations, not
validation performed by generated protobuf classes.

No login, password, token, contact, SNILS, parent or teacher data is included.
Registration names are for trusted server-side storage and published snapshots;
this transport does not authorize exposing them in pre-publication jury JSON.
There are no score, result, start, completeness, pagination or qualification
fields and no registration writes.

## Reproduce contract verification

From the repository root with .NET SDK 10 or later:

```powershell
dotnet build Texnokaktus.ProgOlymp.Common.Contracts.slnx
dotnet run --file tools/VerifyApiReadContract.cs
```

The file-based verifier references the real contracts project, so its checks use
C# generated by the configured Grpc.Tools compiler, not a handwritten DTO. It
requires no additional test project or packages. A successful run prints four
`PASS` lines and exits with code 0. It checks unary methods, allowed fields,
Int32/Int64 types, nesting, optional presence and binary round-trips, including
separate IDs for both stages, absent/present-default/cleared values and empty
rosters. This is contract verification, not evidence of a running API server.

## Consumer delivery

Pin the reviewed Common.Contracts commit separately from legacy bindings and
compile only `proto/Api/ApiReadService.proto` in the API and Judge consumers, with
`proto/` as the protobuf import root. This avoids upgrading existing consumers
whose older Results RPCs have a different wire contract. The shared source ref
and the API implementation must be delivered independently; a source-only change
does not prove that a deployed API supports the new RPCs. No NuGet package or new
release pipeline is required for this source contract.
